## 宿題

- 取り組んだレベル：基礎

- やったこと：
  `app/tools.py` の `search_glossary` の docstring を「query には調べたい用語を1つだけ入れる（例: "LoRA"）」から
  「query には調べたい用語をまとめて入れる（例: "LoRA QLoRA"）」に変更した。
  変更はこの1か所のみで、`app/agent.py` の `INSTRUCTIONS` は変えていない。
  変更前後で同じ2問を、同じモデル（gemini-3.5-flash-lite）・同じコマンド（`--trace` 付き）で実行して比べた。

- 結果：

  | 質問 | 変更前 | 変更後 |
  |---|---|---|
  | 3レベルとは（1語） | {'query': '3レベル'} 1本 / requests=2 / 入力783・出力125 | {'query': '3レベル'} 1本 / requests=2 / 入力779・出力122 |
  | LoRAとQLoRAの違い（2語） | {'query': 'LoRA'} と {'query': 'QLoRA'} の2本 / requests=2 / 入力1196・出力166〜190 | {'query': 'LoRA QLoRA'} の1本 / requests=2 / 入力891・出力215 |

- 気づき・疑問：
  - 2語の質問では、変更前は「1つだけ」の指示に従って2回に分けて（1回の応答で並列に）呼んでいた。
    変更後は1つの query にまとめた。docstring の1行がツール呼び出しの「粒度」を決めている。
  - requests はどちらも2で変わらない。並列に呼んでも requests は増えないため、コストに効いたのは
    入力トークンだった（1196 → 891、約25%減）。ツールの往復が1回分減ったためと考えられる。
  - 情報は失われていない。まとめた query でも `search_glossary('LoRA QLoRA')` は2件（LoRA と QLoRA）を返した。
    1回で2語を調べられるなら、往復を減らしても精度は落ちない。
  - 1語の質問（3レベル）は前後でほぼ変化しなかった（783→779、125→122）。
    変更の効果は「複数語を聞かれたとき」に限定されることが、対照として示せた。
  - 実装は空白を除去して部分一致（`n in q`）で探し、`MAX_RESULTS = 3` で切る。語を3つ以上まとめると
    3件で切られて取りこぼす危険がある。「まとめる」は検索精度とのトレードオフになる。
  - `--trace` の `[tool return]` は先頭120文字で切られるため、表示から「返っていない」と判断してはいけない。
    戻り値の全体は `tools.search_glossary('LoRA QLoRA')` を直接呼んで確認した。
  - 改善案：コストを下げたいなら呼び出し回数より、1回あたりの返り値（件数・定義文の長さ）を削るほうが安全だと考えた。
